# «Роли» показывают правду, а «Сохранить роль» меняет только тронутое (ROLES_SAVE_TRUTH_V1) — дизайн

**Статус:** утверждено владельцем 2026-09-29.
- «Yes, fix it»: экран показывает то, что у роли есть сейчас; «Сохранить роль» меняет только то, что тронули.
- «Ask me to review»: у уже сохранённых ролей — надпись «Проверьте права этой роли»; сами права программа не меняет.

**Основание:** проверка 2026-09-29 на изолированной копии данных. Работали настоящий сервер и настоящий экран в браузере (Playwright), живые данные не тронуты.

**Повод:** владелец написал «call center listening the records … not working on the roles». Прослушивание у штатного оператора работает, это доказано. Зато проверка через «Роли» нашла эту ошибку.

---

## Доказанная ошибка

**Что показывает экран.** `roles-editor.js` рисует `{...grantsFromLegacy(perms), ...perms.grants}`. Если роль ключ не настраивала, экран ВЫВОДИТ уровень из старой галочки раздела: «раздел выдан — внутри всё».

**Что решает сервер.** Для такого ключа сервер пускает по списку ролей в коде (`server/services/gate-fallbacks.js`: `GATE_FALLBACK`, `FALLBACK_FN`, строки `adminDefault`).

**Где ломается.** `collectGrants` пишет матрицу целиком. Поэтому первое же «Сохранить роль», даже без единой правки, превращает догадку экрана в настоящее право.

**Доказано на копии.**
1. «Оператор колл-центра» сохранили без изменений. В роль записалось `crm.all: edit`, и оператор стал читать заявку другого сотрудника (id 1546). До сохранения — пусто.
2. «Регистратор» сохранили без изменений. Записались `inpatient.vitals`, `inpatient.prescriptions`, `inpatient.marks`, `inpatient.discharge` = `edit` и `crm.all: edit`. `admission_vitals_add` от регистратора: до сохранения 403, после — 200.

**Сплошная проверка:** все роли × все ключи с серверными воротами; уровень на экране сравнивался с тем, что дают ворота. На dev и на тестовой клинике :8712 результат одинаковый:

| Роль | Экран показывает выше, чем дают ворота |
|---|---|
| Регистратор | `inpatient.patients`, `.reviews`, `.discharge`, `.prescriptions`, `.marks`, `.vitals`; `crm.all` |
| Медсестра | `inpatient.requests`, `.reviews`, `.prescriptions` |
| Врач | `inpatient.discharge`, `.beds`, `.marks` |
| Главный врач | `inpatient.marks` |
| Старшая медсестра | `inpatient.reviews`, `.prescriptions` |
| Оператор колл-центра | `crm.all` |
| Своя роль клиники | то же, что у её основы |

**Сколько это живёт.** `crm.all` появился в `0770581` (CRM_HEAD_MERGE_TAGS_V1, первый тег v3.9.0) без явного «Нет» у существующих ролей. Миграция 141 для `crm.dial/calls/recording` такое «Нет» написала. Стационарные ключи старше.

**Что смягчает.** Назначения закрыты вторым правилом: `assertCanPrescribe` пускает только лечащего и главного врача. Поэтому это расширение безвредно, прочие — нет.

**Обратная сторона той же ошибки.** Свою роль на основе администратора сервер пускает всюду, пока ключ не настроен, а экран показывает догадку ниже. Сохранение такой роли права СУЖАЕТ.

## Решение

### 1. Сервер говорит, что у роли есть сейчас

**Новое RPC** `role_effective_grants { role }` → `{ levels: { <key>: 'none'|'view'|'edit'|'delete' } }`. Возвращаются только строки справочника, у которых есть серверные ворота, то есть `fallbackLevel(...) !== null`. Уровень — наивысший из уровней строки, который пускают те же ворота:
- **ключ записан у роли** → записанный уровень, с поправкой «закрытый раздел закрывает всё» (`grantAllowsOr`);
- **ключ не записан** → то, что дают ворота по списку ролей основы: `fallbackLevel(db, pseudo, key, 'all')`. Ворот одного уровня бывает несколько, засчитывается уровень, который пускают ВСЕ;
- **своя роль на основе администратора** → как `grantAllowsOr`: администратор проходит, пока его роль ключ не настроила.

**Для кого считается.** Псевдо-пользователь: `{ id: 0, role: <штатная роль или основа своей роли>, extra_roles: [], custom_role_code: <код своей роли или null> }`.

**Кто может спросить.** Тот, кто открывает «Роли»: администратор или `settings.roles` на уровне «Просмотр» и выше. Остальным — 403.

**Лицензия.** Это чистое чтение, поэтому RPC входит в `READ_ONLY_RPCS`.

**Разделы и окна-маршруты оболочки** серверных ворот не имеют и в ответ не входят. Их экран выводит, как прежде: оболочка читает их тем же выводом.

### 2. Экран показывает правду

- При выборе роли экран спрашивает `role_effective_grants` и рисует `{ ...grantsFromLegacy(perms), ...effective.levels, ...perms.grants }`. Правда сервера перекрывает догадку, записанное — всё.
- **Если ответа нет** (сеть, ошибка): роль открывается ТОЛЬКО ДЛЯ ЧТЕНИЯ, кнопка «Сохранить роль» заперта. Строка сверху: «Не удалось узнать, какие права у роли сейчас, — сохранять нельзя. Обновите страницу.» Вернуться к прежней догадке значило бы вернуть ошибку.

### 3. «Сохранить роль» пишет только тронутое

**В `grants` пишется:**
- каждый ключ, уже записанный у роли, — с текущим значением;
- каждый ключ, чьё значение сейчас ОТЛИЧАЕТСЯ от показанного при открытии.

Нетронутый незаписанный ключ не пишется: решать продолжает сервер, ровно так, как экран и показал.

**Уточнения:**
- **Закрыли раздел** — строки обнулились, значит изменились и пишутся как «Нет». Это решение. Страховка `collectGrants` «закрытый раздел обнуляет своих» остаётся.
- **Открыли раздел обратно** — строки вернулись к показанному. Они не пишутся, если не были записаны раньше.
- **Старые поля** `sections/levels` выводятся из ВСЕХ показанных значений, как сейчас (`legacyFromGrants`).
- **«Изменено?»** и снимок сохранённого считаются тем же `collect()`.
- **Подпись:** `collectGrants(controls, { explicit, closed, initial })`, где `initial` — показанные при открытии значения. Прежние правила остаются частными случаями «не тронуто — не пишется»: «строка `adminDefault` не пишется» и «несвершённое „Нет“ раздела не пишется».
- **Защита «Ролей»** для не-администратора (`role-guard.js`) не меняется: пишется меньше ключей, значит и ложных отказов меньше.

### 4. Уже сохранённые роли — «Проверьте права этой роли»

**Миграция 230** (номер проверить перед записью, см. «Порядок работы»). Новая таблица:

```sql
role_grant_reviews (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  role TEXT NOT NULL,
  key TEXT NOT NULL,
  level TEXT NOT NULL,
  standard TEXT NOT NULL,
  found_at TEXT NOT NULL DEFAULT (...),
  resolution TEXT CHECK (resolution IS NULL OR resolution IN ('restored','kept')),
  resolved_at TEXT,
  resolved_by INTEGER REFERENCES users(id),
  UNIQUE (role, key)
)
```

`role_permission_reviews` (миграция 215) не трогаем: у неё `CHECK (area IN (...))`.

**Разовая запись.** Для каждой роли, кроме `admin` и своих ролей на основе администратора, по каждому ключу из `GATE_FALLBACK` строка пишется, если записанный уровень СТАРШЕ стандарта основы. Стандарт — это уровень, который ворота дали бы по списку ролей.

**Таблица стандартов.** Это статичная таблица `VALUES (base, key, standard)`, собранная по `GATE_FALLBACK`. Тест сверяет её с `fallbackLevel` для каждой основы × ключа, поэтому разойтись молча они не могут.

**Поведение миграции:**
- `INSERT OR IGNORE`: повторный накат ничего не добавляет;
- права миграция НЕ меняет.

**На экране «Роли».** У роли с нерешёнными строками — плашка в стиле `roles-review.js`:
- заголовок «Проверьте права этой роли»;
- текст: «У роли есть права выше обычных для её основы: {список названий строк справочника}. До этого обновления экран «Роли» мог выдать их сам — при любом сохранении роли. Если вы выдали их нарочно, оставьте как есть.»

**Кнопки:**
- **«Убрать эти права»** — строка роли перечитывается, названные ключи удаляются из `grants` (решать снова начинает основа), строки отмечаются `restored`.
- **«Оставить как есть»** — отметка `kept`.

После любой из кнопок плашка у этой роли больше не появляется.

**Реестр таблиц** (`schema-registry.js`): читать и менять — как `role_permission_reviews` (администратор или «Роли: Изменение»). Таблица живёт в главном здании, как `role_permissions`.

### 5. Слушать записи — понятнее (мелочь, тот же выпуск)

Всё ниже — про прослушивание записей разговоров.

- **Карточка заявки.** `crm_lead_calls` отдаёт у каждой строки `can_listen` (тот же `mayHear`). «Прослушать» рисуется только при `can_listen`. Иначе под списком одна приглушённая строка: «Слушать записи разговоров вашей роли не разрешено — право «Прослушать запись» в «Роли».»
- **EasyPhone.** `/api/calls` отдаёт `may_hear`, и «Прослушать» рисуется только при нём. Отказ или ошибка показываются ТЕКСТОМ в строке, а не только в подсказке под мышью (сейчас кнопка превращается в «Не вышло», а причина — в `title`).
- **Название строки в «Роли».** Строка `crm.calls` «Звонки и записи разговоров» переименовывается в «Журнал звонков»: журнал записи не открывает. В описании добавляется: «Слушать записи — отдельная строка «Прослушать запись».»

## Тесты (обязательные)

1. **`role_effective_grants`:**
   - оператор: `crm.all` none, `crm.recording` edit, `crm.calls` view;
   - регистратор: `inpatient.vitals` none, `crm.all` none;
   - медсестра: `inpatient.vitals` edit;
   - своя роль на основе оператора — как у оператора;
   - своя роль на основе администратора — верхние уровни;
   - закрытый раздел даёт «none» внутри;
   - медсестре без «Ролей» — 403.
2. **«Открыл и сохранил — ничего не изменилось»,** через настоящий экран (харнесс `roles-editor.test.mjs`). Проверяется для каждой строки `role_permissions` свежей базы после всех миграций, плюс синтетические роли: своя на основе оператора, своя на основе администратора, роль только со старыми полями, роль с записанными ключами. Условия:
   - `grants` те же как словарь (те же ключи и значения; порядок ключей не важен);
   - `sections/levels` те же как множества;
   - уровни ворот по каждому ключу — те же.
3. **Тронул один ключ** — в `grants` добавился ровно он.
4. **Сторож:** для каждого ключа с воротами и каждой штатной роли показанное значение незаписанного ключа равно ответу `role_effective_grants`. Новый ключ с воротами не сможет вернуть догадку.
5. **Два доказанных сценария — сквозные, на сервере:** после «пустого» сохранения оператор не читает чужую заявку, а `admission_vitals_add` регистратора остаётся 403.
6. **Миграция 230:**
   - отмечает ровно расширенные пары (роль, ключ);
   - пропускает администратора и роли на его основе;
   - повторный накат ничего не добавляет;
   - таблица стандартов равна `fallbackLevel` для всех основ × ключей;
   - «Убрать» снимает только названные ключи, «Оставить» их сохраняет;
   - плашка исчезает после любой из кнопок.
7. **Прослушивание:**
   - карточка без права — кнопки нет, есть строка-пояснение; с правом — кнопка есть;
   - EasyPhone при `may_hear: false` кнопку не рисует;
   - текст ошибки виден.
8. **Переводы:** все новые фразы — в ru/uz/en (uz латиницей, en без кириллицы); проверки покрытия переводов проходят.
