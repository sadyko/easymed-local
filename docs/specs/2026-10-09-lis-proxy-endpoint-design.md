## Цель

LIS Proxy — служба Windows на лабораторном ПК. Она говорит с анализатором на его протоколе и на каждое значение шлёт HTML-форму POST на один адрес, который выбираем мы. Easy-Med становится этим адресом:

1. **принимает результаты** BS-200, BC-780 и AutoLumo A1000 и раскладывает их по бланкам по тем же правилам, что и свой порт LIS;
2. **отвечает на запрос рабочего списка**: BS-200 сканирует пробирку и получает из Easy-Med тесты её оплаченного заказа.

Два обещания, ради которых всё остальное:
- **ни одно значение не теряется по вине Easy-Med.** Программа шлёт каждое значение один раз и не повторяет, а анализатору уже ответила «принято»;
- **ни одно значение не ложится чужому пациенту.** Номер пациента, номер места, номер контроля — не номер пробирки.

## Провод LIS Proxy (договор §2 — факт)

| | |
|---|---|
| Запрос | `POST <api_url>` как настроено; **строка запроса сохраняется** — ключ передаётся в `?key=`. `Content-Type: application/x-www-form-urlencoded`, `User-Agent: Mozilla/5.0`, `Accept-Language: en-US,en;q=0.5`, **`Accept-Encoding: gzip`**. Тело — ключи в скобках, как в PHP (`lisResult[R][res]`). |
| Повтор | **Нет.** Одна попытка; отказ соединения, тайм-аут или не-2xx → «Error while sending results to API», значение потеряно. На диске прокси ничего не хранит. |
| `apiResultSave` | Одно значение: `lisResult[name]` (имя анализатора в прокси), `[host]` (подпись, свободный текст), `[barcode]`, `[code]`, `[R][res]`, `[R][unit]`, `[R][norms]`, `[R][flag]`. Любой ответ 2xx принят (измерено на одиночных значениях; руководство поставщика `LIS-API.md`, §2, требует ровно `Ok` — Р23). Значения одной пробирки идут подряд отдельными запросами, в порядке анализатора, с паузой `timeout_ms` (по умолчанию 100 мс). |
| `apiOrderGet` | `order[name]`, `order[host]`, `order[barcode]`. Ответ — JSON `{"0":{clientId, surname, name, date_birth, sex, biomaterial_code, code}, "1":{…}}`, **каждый ключ в каждой записи обязателен**. `date_birth` — только `dd.MM.yyyy`; `sex` `"1"` → M, `"0"` → F, иное → пусто; `code` — код теста на анализаторе. «Не найдено» = `{}` (прокси тогда анализатору не отвечает, BS-200 ждёт до тайм-аута). Руководство поставщика (`LIS-API.md`, §3) велит ровно текст `Order not found` — на программе не проверялся; выбор — Р26. |
| `apiBarcodeListGet` | `order[name]`, `order[host]`. `{}` — пустой список, безопасно. Руководство поставщика (§4) — `Order not found`; тот же выбор, Р26. |
| Откуда штрихкод | BS-200 — **PID-2, если не пусто**, иначе OBR-2. BC-780 — OBR-3 (верно). AutoLumo (ASTM) — O-3.2, **только последние 8 знаков** (`LAB-000777` → `B-000777`); короче 8 — прокси падает, значение потеряно. BC-20/BC-5300 — «поле 3 третьей строки» (`Therapy^^12`, `6690-2^WBC^LN`, пусто). |
| Мусор | BC-780 шлёт `code=IS` с пустым значением; BC-20/BC-5300 — `Take Mode`, `Test Mode` как значения. |
| Что видит анализатор | ACK уходит анализатору ДО запроса к Easy-Med. Рабочий список BS-200 — `QCK^Q02` + `DSR^Q03`: DSP-1 и DSP-3 = `clientId`, DSP-4 = дата рождения, DSP-5 = пол, DSP-21 = штрихкод запроса, DSP-26 = биоматериал, DSP-29… = коды. |

## Решения этого дизайна (там, где выбор был за нами)

| № | Решение | Почему (одна строка) |
|---|---|---|
| Р1 | Настройка — файл `data/lisproxy.json` (`enabled`, `key`, `changed_at`, `changed_by`), запись атомарная (`writeAtomic`, `control/checkin.js`); чтение никогда не бросает (испорчен — выключено). | Миграции — только ADD COLUMN, а таблицы настроек у лаборатории нет; так уже живёт секрет пары филиалов (`branch-sync/pairing.js`): у здания свой, в `/api/db` и в синхронизацию не попадает. |
| Р2 | Ключ — 32 случайных байта в base64url (43 знака, без `+ / =`); сравнение — SHA-256 обеих строк и `timingSafeEqual` по 32 байтам. | Время сравнения не зависит ни от длины, ни от совпавших знаков; base64url безопасен в кавычках командной строки Windows и в TOML. |
| Р3 | Ключ проверяется **до** разбора тела. Выключено, нет ключа, не тот, ключ массивом (`?key=a&key=b`), ключ только в теле, не POST, лишний путь (`/api/lisproxy/x`) — один и тот же ответ 404 с телом `app.js` для неизвестного адреса. Ничего не пишется, прибор не заводится, «на связи» не ставится. | Отказ неотличим от отсутствия адреса (образец — `telephony/webhooks.js`); чужое тело не разбирается вовсе. |
| Р4 | Журнал — строка `lab_device_messages`, вставленная первой (сырое тело — в новую колонку `source_body`). Всё дальнейшее **дописывает эту же строку** (`recordMessage({ id })`), а не заводит вторую. | Одна строка на запрос: лента, лоток, счётчики и серия видят ровно то, что видят сегодня; время прихода — время записи. |
| Р5 | Ответ прокси никогда не сжимается: `Content-Encoding: identity` (`compress.js` такой ответ пропускает). | Прокси шлёт `Accept-Encoding: gzip`, а `compress.js` жмёт JSON от 1 КБ — рабочий список BS-200 на 8+ тестов; распаковывает ли прокси gzip, не проверено, а испорченный JSON = анализатор без заказа. |
| Р6 | В синтетическом ORU MSH-3 = `LISPROXY` (постоянное), MSH-4 = `LabPC`, OBX-3 — код одним компонентом. Имя анализатора в прокси в HL7 не идёт. Провод (ревью I2/I3) — `lisproxy-chem` (BS-200: D6, хвостовые нули), `lisproxy-autobio` (A1000: флаги D9 из поля `flag`) или `lisproxy` (прочие — как `forwarder`): поля — как у переадресателя, правила значения и флага — модели строки, как у своего порта. | Приём угадывает модель по MSH-3 (`guessProfile`, `ingest.js:1091`); имя в прокси — свободный текст, а модель выбирает только человек. |
| Р7 | Прибор LIS Proxy: `via = 'lisproxy'`, имя в прокси — `proxy_name`, подпись — `proxy_label`, адрес лабораторного ПК — `proxy_ip` (новые колонки). `host` = `''`, `sending_app` = NULL. | Триггер мигр. 233 (`trg_lab_devices_address_unstamp`) на смену `host` у BS-200 снимает подтверждения; `guessProfile` по `sending_app` (`ingest.js:685`) угадывал бы модель по имени. |
| Р8 | Кто прибор (ревью I5 — подпись важнее адреса). Подпись названа: (1) строка `via='lisproxy'` с тем же именем и той же подписью (без учёта регистра) — на этом адресе, иначе **ровно одна** такая: адрес сменился (DHCP), `proxy_ip` переписывается молча; (2) иначе строка с тем же именем и адресом **без** подписи — та же, подпись запоминается; (3) иначе — новая находка: чужая непустая подпись на том же адресе — другой ПК, подпись строки не переписывается никогда. Подписи нет: (имя, адрес), иначе единственная строка без подписи — адрес сменился. Новая находка — `discovered = 1`, `added = 0`, модель пустая, не больше 20 находок LIS Proxy. | Два ПК с одинаковым именем анализатора различаются адресом и подписью (`-host <имя ПК>`); при сомнении — лишняя видимая строка, а не склейка двух приборов (то же правило, что `discover.js`, шаг 2). |
| Р9 | Значение: одна десятичная запятая без точки → точка (`5,1` → `5.1`, `wire.js decimalPoint`); число ровно с шестью знаками после точки — без хвостовых нулей (`5.100000` → `5.1`, `wire.js trimZeros`) — и в норме тоже; NM — только `^-?\d+(\.\d+)?$`, иначе ST. | Шесть знаков — `%f` программы BS-200; свой порт делает с BS-200 то же; `0.50` гематологии остаётся как пришло. |
| Р10 | `B-\d{6}` → `LAB-\d{6}` и `-[1-9]\d{6}` → `LAB-\d{7}` (ревью I4: семь цифр у этикетки — номер от 1 000 000; `-0000777` — хвост чужого номера) — **только у прибора с моделью AutoLumo A1000**. У прочих (и у находки без модели) — в лоток с подсказкой «похоже на обрезанную этикетку AutoLumo — выберите модель». | Догадка не выбирает пациента; находка всё равно ничего не пишет (N2). |
| Р11 | Не номер пробирки → строку лотка пишет сам вход (в сыром ORU OBR-3 пуст), в приём не идёт. Плюс своя стена в `ingest.js`: у прибора LIS Proxy номер без `LAB-` не ищет заказ (кроме «Привязать» человеком). | Причина говорит о прокси («LIS Proxy прислал не штрихкод пробирки…»), «Привязать» работает (OBX в сыром есть), а приём не зависит от того, что вход не ошибся. |
| Р12 | Запрос без строки прибора (имя пустое или предел находок) — в лоток «прибор не заведён», в приём не идёт. | Приём без прибора пишет в панель с кодами производителя (`ingest.js:690-695` отказывает только у BS-200; R3 п. 1) — для LIS Proxy это значило бы писать от неизвестного. |

## 1. Вход: адрес и ключ

- **Адрес:** `POST /api/lisproxy`. Маршрут `server/routes/lisproxy.js` (`lisProxyRoutes(db, dataDir)`), в `server/app.js` — **до** общих разборщиков тела (`express.json`) и до `app.use('/api', requirePasswordChanged)` (ревью I1: разборщик, стоящий раньше, отказал бы большому телу или съел бы его). Сессии у прокси нет.
- **Порядок внутри маршрута:**
  1. ключ (Р3) — по `req.query.key`, до тела;
  2. тело — **байтами**, до любого разбора (ревью I1): распаковка gzip/deflate/br, предел 2 МБ (сверх — сохранены первые 2 МБ, не разбирается); текст — UTF-8, иначе объявленная кодировка или windows-1251 с отметкой в журнале. Разбор — свой (`lisproxy-form.js` `parseProxyForm`: ключи в скобках как в PHP, до 10 000 пар, повтор ключа — последнее значение, у `method` — первое, имя запроса без учёта регистра). Запрос результата узнаётся и по сырому тексту (`method=apiResultSave`): ответ `Ok`, даже если тело не разобралось (тогда строка — в лотке). Прежний `express.urlencoded` отказывал телу больше 100 КБ, больше 1000 пар, не формой или не в UTF-8 — ни тела в журнале, ни `Ok`;
  3. журнал (раздел 2);
  4. обработка (разделы 3–6);
  5. ответ (Р5, Р23).
- **Общий JSON-разборщик** `/api` стоит после входа и тело прокси не видит.
- **Лицензия** — не проверяется (решение 5). `attachControl` (`app.js:109`) только кладёт состояние в запрос и ничего не запрещает.
- **Адрес отправителя** — `req.socket.remoteAddress` без `::ffff:`, никогда не `X-Forwarded-For`.
- **Настройка** (Р1, Р2): `server/lis/lisproxy-settings.js` — `readProxySettings(dataDir)`, `writeProxySettings(dataDir, next)`, `newProxyKey()`, `keyMatches(given, stored)`. Файл читается на каждом запросе (меньше 1 КБ) — смена ключа действует сразу.
- **Адрес для прокси** показывает экран: `http://<адрес ПК в сети>:<порт>/api/lisproxy?key=<ключ>`. Адреса — `lanAddresses()` (`branch-sync/pairing.js:674`), порт — `process.env.PORT || 8000` (как `server/index.js:230`).

## 2. Сначала журнал, потом всегда 200

1. После ключа и разбора — **одна вставка** в `lab_device_messages`:
   - `raw = ''`, `status = 'rejected'`, `detail = 'LIS Proxy: запрос сохранён, разбор не завершён'`;
   - `kind`: `result` у `apiResultSave`, иначе `query`;
   - `peer` — адрес; `source_body` — тело как пришло.
   Не записалась — `500 { error: { code: 'internal', message: 'Ошибка сервера. Повторите позже.' } }`: значение потеряно в любом случае, а прокси напишет «Response Code : 500» в свой журнал.
2. Дальше всё в `try`. Каждый исход дописывает ЭТУ строку (`recordMessage({ id, … })`: `device_id`, `raw`, `sample_id`, `visit_service_id`, `status`, `detail`, `kind`, `resolved_at`, `disputes`). `source_body` после вставки не меняется никогда.
3. Ответ — **200 на каждый исход**: «не нашли заказ», «не подтверждено», «не оплачен», мусор, находка — состояния лотка, а не ошибки HTTP.
4. Исключение после журнала — строка `rejected` с `detail = 'LIS Proxy: ошибка разбора — <сообщение>'` (запись — по возможности), ответ 200 (`Ok` или «ничего», Р26). Сорвавшаяся транзакция приёма уже сама пишет `rejected` «ошибка записи: …» в ту же строку (`ingest.js:1294`).
5. Тело в консоль не печатается никогда.

## 3. Результат (`apiResultSave`)

### 3.1 Путь

1. Прибор (раздел 4): найти или завести; `device_id` — в строку журнала; «на связи» (`touchDevice`) — на **каждом** запросе с ключом, в том числе мусоре, лотке и рабочем списке.
2. Мусор (3.4) → строка разрешена, ответ `Ok` (Р23).
3. Прибора нет (Р12) → лоток «LIS Proxy: прибор не заведён — <причина> — значения не записаны».
4. Штрихкод (3.5): не номер пробирки → лоток с причиной (Р11).
5. Синтетический ORU (3.2) → `receiveMessage(db, raw, { peer, deviceId, journalId })` — прежний вход своего порта. Ответ прибору, который он строит, не нужен и выбрасывается. Через `receiveMessage` проходит и правило «прибор выключен» (`receive.js:135-144`).
6. Сменился адрес (Р8, п. 2) → к журналу строки: «адрес LIS Proxy сменился: A → B».

### 3.2 Сообщение

Одно значение — одно сообщение (сегменты через `\r`):
```
MSH|^~\&|LISPROXY|LabPC|||<yyyyMMddHHmmss местное>||ORU^R01|<номер строки журнала>|P|2.3.1||||0||UNICODE
PID|1
OBR|1||<LAB-…, или пусто, если не номер пробирки>
OBX|1|<NM|ST>|<код>||<значение>|<единица>|<норма>|<флаг>|||F
```
- **Провод `lisproxy*`** (ревью I2/I3; `wire.js wireDecision`: MSH-3 = `LISPROXY` и MSH-4 = `LabPC`, по модели строки — см. Р6; поля — как у `forwarder`): номер — OBR-3, код — OBX-3 (компонент 1, затем 2), значение — OBX-5 целиком, флаг — OBX-8, норма прибора — OBX-7. Провод профиля строки не участвует (`wireDecision` при `LabPC` спора не даёт).
- **Код — один компонент** (`GLU`, а не `GLU^GLU`, как в документе). Почему этого хватает:
  - сопоставление сравнивает компонент 1 или 2 (`match.js:169`);
  - «Поле анализатора» сохраняет имя, а без имени — код (`lab-device-codes.js` `codeChoices`);
  - тексты лотка показывают OBX-3 целиком (`match.js:225`) — «не использованы: P-LCR» вместо «P-LCR^P-LCR».
- **Проверено** на коде этого дерева (зонд в scratchpad):
  - `wireDecision` → `forwarder`, без спора; `guessProfile` → null;
  - номер → `LAB-000123` из OBR-3;
  - серия BS-200 из двух таких сообщений — «серия из 2 сообщений принята», `5.1` в бланке.
- **В сыром — только синтетический ORU.** Его перечитывают:
  - пересчёт серии (`ingest.js:291-311`);
  - `deliveredValue` (`:527-533`);
  - «Привязать» (`rpc/lis.js:230`);
  - `lis_device_codes` (`rpc/lis.js:363-376`).
  То, что прислала программа, лежит в `source_body` (правило «сырое — то, что пришло» остаётся честным).

### 3.3 Экранирование, NM/ST

- Каждое поле: `\` → `\E\`, `|` → `\F\`, `^` → `\S\`, `&` → `\T\`, `~` → `\R\`; перевод строки → пробел (иначе он разорвал бы сегмент).
- Приём экранированное не раскодирует: единица `10^9/L` ляжет в сырое как `10\S\9/L` и так и покажется в «Поле анализатора». Это только показ: единица бланка — из панели (инвариант 4).
- Значение — Р9. Флаг прибора — как пришёл; без диапазона клиники `N` даёт «Норма» только при норме прибора в OBX-7 (`ingest.js:556-568`).

### 3.4 Мусор: строка журнала разрешена, без лотка, без серии

Одна константа `PROXY_SERVICE_CODES` в `server/lis/lisproxy-form.js`:
- значение пусто или только `*`;
- код (без учёта регистра) — `Take Mode`, `Test Mode`, `Blood Mode`, `Ref Group`, `Remark`, `Age`, `IS`;
- гистограммы Mindray (`WBC/RBC/PLT Histogram…`) и `Qc Level` (ревью I6: прежнее «код с пробелом, а значение не число» прятало настоящие ответы — «HIV Ag» = «Positive» — в справку; снято);
- «нет результата» Mindray (`wire.js isNoResult`: число ≤ −100000000; Р24).

Причина пишется словами: «LIS Proxy, справка: служебная строка прибора «Take Mode»», «… пустое значение («IS»)», «… прибор: нет результата «-268435455» (GLU)».

### 3.5 Штрихкод (только строки LIS Proxy)

| Пришло | Итог |
|---|---|
| `LAB-\d{6,}` (регистр не важен) | как есть, в виде `LAB-…` |
| `B-\d{6}` / `-\d{7}`, модель строки — AutoLumo A1000 | `LAB-\d{6}` / `LAB-\d{7}` (последние 8 знаков этикетки) |
| всё прочее (пусто, `^` внутри, голые цифры, `PATNUM9`, `B-000777` у другой модели) | лоток `unmatched`, `visit_service_id` = NULL, `sample_id` = как пришло; причина — ниже |

Причина начинается с «LIS Proxy прислал не штрихкод пробирки: <как пришло>», дальше — что делать:
- с `^` — «— проверьте тип анализатора в LIS Proxy (BC-20/BC-5300 путают поле)»;
- одни цифры — «— похоже на номер пациента или места, а не пробирки: на анализаторе сканируйте этикетку LAB- в поле штрихкода, номер пациента не заполняйте; пробу привяжите кнопкой «Привязать»»;
- `B-…` / `-…` у не-AutoLumo — «— похоже на обрезанную этикетку AutoLumo: если это AutoLumo A1000, выберите эту модель у прибора в «Анализаторах»»;
- пусто — «(пусто) — анализатор не передал номер пробы»;
- иначе — «— проверьте настройку штрихкода на анализаторе и тип анализатора в LIS Proxy; если это проба вашего заказа — нажмите «Привязать»».

**Голые цифры не ищут заказ никогда** (решение 3). Правило своего порта «номер с этикетки, открытый заказ не старше 7 дней» (`ingest.js:1019-1049`) у строк LIS Proxy не действует ни в одном месте: вход до него не доходит (Р11), а у приёма своя стена — строка LIS Proxy без этикетки `LAB-` в OBR-3 → лоток «LIS Proxy прислал не штрихкод пробирки…», заказ не ищется. Исключение — «Привязать»: номер называет человек (`sampleIdOverride`).

### 3.6 Серия — всегда, по строке прибора

- Прокси шлёт одно значение в запросе. Поэтому у строк LIS Proxy:
  - `oneTest` (`ingest.js:1125`) истинно **при любой модели**;
  - отправитель серии — `m.device_id = ?` (`ingest.js:277`, `who.perInstrument` в `:1213`), а не «та же модель».
- Без этого каждое значение BC-780 легло бы в лоток «не пришли: …» (зонд это подтвердил: HGB → «не пришли: Лейкоциты (WBC)», хотя WBC уже в бланке).
- Окно серии, правило «повтор», «ждём остальные строки», 200 сообщений на заказ — прежние (`match.js:339-356`, `:441`, `:514`).

### 3.7 Гематология: лишний показатель — справка (Р14)

У строки LIS Proxy с моделью вида `hematology` (BC-780) значение, которое ничего не заполнило и ни на что не претендует, — это строка, которая:

## 4. Прибор LIS Proxy

### 4.1 Кто он (Р7, Р8)

- `ensureProxyDevice(db, { name, label, ip })` — в `server/lis/discover.js`, рядом с `ensureDevice`:
  - ищет **только** среди `via = 'lisproxy'`;
  - имя — `lisResult[name]` / `order[name]`, без учёта регистра;
  - подпись — `[host]`;
  - адрес — `peer`.
- Новая находка:
  - `name` — имя в прокси (если занято — «имя (подпись)»);
  - `profile = ''`, `transport = 'mllp'` (CHECK мигр. 123), `host = ''`, `port = NULL`, `enabled = 1`, `discovered = 1`, `added = 0`.
- Предел — 20 находок LIS Proxy (`MAX_PROXY_FOUND`); свой порт — отдельно, как был (20).
- **Смена адреса** пишет только `proxy_ip`. Триггер мигр. 233 смотрит `host` и `port`, поэтому `code_epoch` и подтверждения BS-200 остаются.
- Это закрывает «два BS-200 под DHCP меняются адресами» только для пути LIS Proxy: различает подпись. В инструкции — «`-host` — имя этого ПК, у каждого ПК своё».

### 4.2 Свой порт не видит строк LIS Proxy

- `ensureDevice` (`discover.js:167`): `via IS NULL` во всех четырёх запросах:
  - адрес (`:188`);
  - находки без адреса (`:252`);
  - «заведён человеком без адреса» (`:286`);
  - счёт находок (`:298`).
  Иначе строка прокси с именем «Mindray» (у неё `sending_app` пуст, `host` пуст) забрала бы MLLP-сообщение по имени (шаг 2).
- Слушатели (`lis/index.js:305`): `AND via IS NULL` — у строки прокси нечего слушать и некому звонить.

### 4.3 «На связи»

`touchDevice` — на каждом запросе с ключом, у которого есть строка прибора. Приём (`ingest.js:984`) отмечает ещё раз — безвредно.

Замечание к документу: «известной ошибки» (отметка только у принятых) в этом дереве уже нет — `LIS_ANALYZER_LIST_V1` отмечает каждое разобранное сообщение. Но строки лотка и мусор LIS Proxy до приёма не доходят — поэтому отметка ставится на входе.

### 4.4 «Добавить» и «Изменить»

- `lis_device_add` (`rpc/lis.js:542`) для `via = 'lisproxy'`:
  - модель обязательна и одна из `PROXY_MODELS = ['mindray-bs-200', 'mindray-bc-780', 'autobio-autolumo-a1000']` (общий список в `public/js/admin/views/lab-devices-lists.js`: его читают и сервер, и экран);
  - `generic` — отказ с текстом Р21.
- «Изменить» у строки прокси:
  - адрес, порт, вид подключения и «Easy-Med подключается сам» не показываются;
  - вместо них — «Подключение: через LIS Proxy — адрес меняется сам, править его не нужно»;
  - модель — из тех же трёх.
- Подтверждения кодов — как сегодня, у строки прокси. Подтверждения со строки MLLP не переносятся.
- Панель с кодами производителя (BC-780) принимает и строку прокси той же модели (правило «та же модель», `ingest.js:696-717`). У BS-200 — только свою строку.

## 5. Рабочий список (`apiOrderGet`)

1. Прибор (4.1), «на связи».
2. `{}` с причиной в журнале, если:
   - строки прибора нет;
   - прибор не добавлен («прибор ещё не добавлен — «Добавить прибор» → «Найдены в сети» → «Добавить»»);
   - прибор выключен;
   - не номер пробирки по 3.5 (`ORU^R01`, `QRY^Q02`, `ALL`, `N`, метка времени, пусто).
3. `worklistLines(db, { deviceId, orderId })` (`ingest.js`) — те же ворота, что у результата. `{}`, если хоть одно не выполнено:
   - заказ есть, `services.is_lab = 1`;
   - статус в `LAB_RESULT_STATUSES` (`visit-status-guard.js:46`), причина — `gateRefusal` («заказ ещё не оплачен…», «заказ отменён», «по заказу возврат»);
   - заказ не выдан (Р16);
   - `orderSide`:
     - панель услуги есть и привязана к этому прибору, или к прибору той же модели, если модель позволяет;
     - у BS-200 — только к своему;
     - подтверждения BS-200 — для этого прибора и его эпохи (устаревшие — «не подтверждено»).
4. Строки:
   - подтверждённые (`confirmedCode`) строки панели заказа пробирки, затем — открытых оплаченных невыданных заказов того же визита, которые кормит этот прибор (Р15);
   - порядок панели, коды без повторов (без учёта регистра);
   - нет ни одной — `{}` «у панели нет подтверждённых кодов этого прибора».
5. Ответ: по записи на код, ключи `"0"`, `"1"`, …:
   ```json
   {"0":{"clientId":"LAB-000123","surname":"","name":"","date_birth":"03.02.1990","sex":"1","biomaterial_code":"serum","code":"GLU"}}
   ```
   - `clientId` — номер пробирки в виде `LAB-…` (и при запросе `B-000123` от AutoLumo);
   - `date_birth` — `patients.date_of_birth` как `dd.MM.yyyy`; нет даты — `""` и в журнале «дата рождения не указана — прибор получит пустую дату»;
   - `sex` — `male` → `"1"`, `female` → `"0"`, иначе `""`;
   - `biomaterial_code` — Р17, по услуге заказа пробирки;
   - `code` — код прибора, как подтверждён.
6. Журнал (Р18):
   - `detail` — «LIS Proxy: рабочий список по пробирке LAB-000123 — отдано тестов: 2 (GLU, UREA)» или «… — ничего не отдано: <причина>»;
   - `reply_body` — JSON ответа;
   - `sample_id` — номер (как восстановлен или как пришёл).

## 12. Известные ограничения

- **Потеря при выключенном Easy-Med** — свойство прокси: повтора нет. Инструкция говорит «Response Code : 0 — прогоните пробирки ещё раз». Просьба к поставщику — §6 документа.
- **Каждое значение — свой запрос.** Контроль BS-200 и BC-780, находка до «Добавить», номер пациента в поле штрихкода — по строке лотка на значение. Экран группирует (Р22), но в базе их столько же. Вопрос владельцу 1.
- **Повтор пробирки на BC-780 в пределах 60 минут** — «повтор» по каждому изменившемуся показателю (правило серии). На своём порту — одна строка (N1). На экране — одна группа.
- **Пустая дата рождения** — прокси пишет в DSP-4 `0000000000`. Примет ли это BS-200, проверяется в сквозной проверке настоящей программой.
- **Номер с этикетки без `LAB-`** (`000123`), набранный на анализаторе, через прокси не принимается (решение 3), в отличие от своего порта. Инструкция велит сканировать этикетку.
- **Резервная копия базы** не содержит `data/lisproxy.json`. Восстановление на другом ПК — «Включить» заново (новый ключ). Адрес у ПК всё равно новый, и лабораторные ПК перенастраиваются.
- **Unicode из ПК анализатора** — коды тестов латиницей (как сегодня, D10).
- **Два ПК с одинаковым именем анализатора без подписи** (или с одинаковой подписью) не различаются при смене адреса — строка «переедет». Инструкция: `-host` — имя ПК, у каждого своё; с подписью (ревью I5) чужой ПК на старом адресе — новая находка.
