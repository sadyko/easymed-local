# Cust Dev — обзвон пациентов после визита

Дата: 2026-08-25 · Статус: спецификация согласована, план не написан

## Задача

Колл-центр обзванивает пациентов, которые **пришли и оплатили услуги**, и выясняет,
довольны ли они. Опыт разбирается не целиком, а по трём точкам внутреннего CJM:
**регистратура**, **касса**, **врач**. Из трёх оценок автоматически складывается
статус карточки на канбан-доске.

Правило владельца дословно: три «доволен» — карточка в «Доволен»; два — в «Частично
доволен».

## Принятые решения

| Вопрос | Решение |
|---|---|
| Единица карточки | Один **визит** (пришёл + есть оплата). Два визита — две карточки. |
| Колонки доски | 5: Не обзвонён · Не дозвонились · Доволен · Частично доволен · Недоволен |
| Значения оценки | Не оценено · Доволен · Не доволен · **Не применимо** |
| Кто оценивается | Регистратор, кассир и врач **поимённо**, снимок на момент создания карточки |
| Когда карточка появляется | На **следующий день** после визита |
| Доступ | **Владелец (`admin`) и колл-центр (`callcenter`)** — больше никто |
| Обязательный комментарий | Да, если хотя бы одна оценка «Не доволен» |
| В первой версии | Доска + попап оценки + **Отчёт** + **выгрузка в Excel** |

## Почему «Не применимо» обязательно

Визит бывает только лабораторный — врача не было. Услуга бывает бесплатной — кассира
не было. Без «Не применимо» такая карточка не смогла бы получить три «доволен»
НИКОГДА и навсегда осела бы в «Частично доволен», а отчёт по врачам считал бы
несуществующего врача недоработавшим.

## Данные — миграция `078_custdev.sql`

Одна таблица, одна строка на визит.

```
custdev_cards
  id              INTEGER PK
  visit_id        INTEGER NOT NULL UNIQUE REFERENCES visits(id)
  patient_id      INTEGER NOT NULL REFERENCES patients(id)
  visit_date      TEXT NOT NULL              -- снимок: доска фильтрует и сортирует по нему
  paid_amount     REAL NOT NULL DEFAULT 0    -- снимок: сумма оплат по визиту

  registrar_id    INTEGER REFERENCES users(id) ON DELETE SET NULL
  cashier_id      INTEGER REFERENCES users(id) ON DELETE SET NULL
  doctor_id       INTEGER REFERENCES users(id) ON DELETE SET NULL

  score_registrar TEXT NOT NULL DEFAULT 'unrated' CHECK (score_registrar IN ('unrated','good','bad','na'))
  score_cashier   TEXT NOT NULL DEFAULT 'unrated' CHECK (score_cashier   IN ('unrated','good','bad','na'))
  score_doctor    TEXT NOT NULL DEFAULT 'unrated' CHECK (score_doctor    IN ('unrated','good','bad','na'))

  status          TEXT NOT NULL DEFAULT 'new'
                    CHECK (status IN ('new','unreachable','satisfied','partial','unsatisfied'))
  comment         TEXT NOT NULL DEFAULT ''

  called_by       INTEGER REFERENCES users(id) ON DELETE SET NULL
  called_at       TEXT
  created_at      TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now'))
  updated_at      TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now'))
```

Индексы: `UNIQUE(visit_id)` (он же гарантия идемпотентности синхронизации),
`idx_custdev_status_date(status, visit_date)`, `idx_custdev_patient(patient_id)`.

**`ON DELETE SET NULL` на всех ссылках в `users` — не украшение.** `routes/users.js`
решает «можно ли удалить сотрудника» по жёстко зашитому списку таблиц, которого эта
таблица не знает; обычный FK позволил бы объявить удаление разрешённым и умереть на
нём непрозрачной пятисоткой. Та же ловушка описана в 073 и 076.

**Телефон и ФИО пациента в таблице НЕ хранятся.** Они читаются живыми через embed
`patients`: если пациент исправил номер, звонить надо по новому. Снимками остаются
только `visit_date` и `paid_amount` — факты о том конкретном визите.

## Как появляются карточки

Никакой фоновой работы и **ни одной правки в денежном коде**. Открытие доски
вызывает `custdev_sync`, один идемпотентный `INSERT … SELECT … WHERE NOT EXISTS`.

Визит попадает на доску, когда одновременно:

1. `visits.status = 'arrived'`;
2. существует счёт визита с `paid_amount > 0` и статусом `paid` или `partial`;
3. локальная дата визита **строго меньше сегодняшней** — правило «звоним на следующий
   день».

`visits.visit_date` хранит **полный UTC-момент** (`new Date().toISOString()` из
`doctor-room.js`, `room-calendar.js`, `requests-inbox.js`), а не голую дату. Поэтому
сравнивать надо `localDate('v.visit_date') < today(db)` из `domain/day.js` — ни
голым `<`, ни `substr(visit_date,1,10)`. База хранит UTC, клиника живёт по местным
суткам: на UTC+5 вечерний визит по UTC-срезу оказался бы завтрашним и карточка
появилась бы на день позже. Так же поступает `queue.js` (строка 65); `date('now')`
или `date(col)` своими руками не пишет никто — это правило `day.js`.

Снимок сотрудников:

- **регистратор** — `invoices.created_by` самого раннего счёта визита (смету составляет он);
- **кассир** — `payments.cashier_id` последнего платежа по этим счетам;
- **врач** — `visits.doctor_id`, а если он пуст — первый `visit_services.doctor_id`
  (лабораторный визит своего врача не имеет).

**Окно синхронизации ограничено.** Синхронизируется пересечение выбранного периода с
последними **90 днями** (`CUSTDEV_BACKFILL_DAYS`). Иначе первое открытие доски в
клинике с двухлетней историей создало бы десятки тысяч карточек «Не обзвонён» —
очередь, которую никто никогда не разберёт. Уже созданные карточки остаются видимыми
в любом периоде; ограничение касается только создания новых.

Прецедент такого «подмета при загрузке» в проекте уже есть — авто-`no_show` в
`public/js/admin/views/crm.js` (строка 170).

## Правило статуса

Считается **на сервере**, в `custdev_rate`, чтобы инвариант держался независимо от
того, что прислал браузер. Считаются только критерии, не помеченные «Не применимо»:

| «Не доволен» среди применимых | Статус |
|---|---|
| 0 | **Доволен** (`satisfied`) |
| ровно 1 | **Частично доволен** (`partial`) |
| 2 и более | **Недоволен** (`unsatisfied`) |

Сохранение оценки отклоняется, если:

- заданы не все три критерия (`unrated` не сохраняется — на телефоне сейчас человек,
  спросить можно про всё, а «не применимо» есть отдельным значением);
- все три помечены «Не применимо» (оценивать нечего, и «Доволен» тут был бы враньём);
- хотя бы одна оценка «Не доволен», а комментарий пуст. Жалоба без причины клинике
  бесполезна, а оператор держит человека на линии именно сейчас.

`called_by` и `called_at` проставляются сервером при сохранении.

### Почему колонки Cust Dev — НЕ данные, в отличие от CRM

Миграция 077 (`CRM_CONFIG_V1`) сделала колонки канбана CRM настраиваемыми: `crm_stages`,
экран «Настройки → CRM», добавление колонки без релиза. Для Cust Dev это сознательно
**не повторяется**.

Колонки CRM — подписи к состояниям, которые двигает человек. Три из пяти колонок
Cust Dev — арифметика по правилу 0 / 1 / 2+. Дать владельцу добавить шестую значило бы
завести колонку, в которую никакая комбинация оценок карточку не положит: пустой
столбец без причины. Переименование тоже опасно — «Доволен» здесь не название вкуса, а
утверждение «ни одной жалобы», и переименовать его в «Хорошо» значит разойтись с
отчётом. Набор из пяти фиксирован в коде.

### Следствие, которое надо назвать вслух

Три из пяти колонок — **вычисляемые**. Перетащить карточку в «Доволен» нельзя:
перетаскивание противоречило бы оценкам, из которых эта колонка и получилась.
Перетаскивание работает только между «Не обзвонён» и «Не дозвонились». Всё
остальное движется оценкой, а не мышью. Это и есть «статусы меняются автоматически».

## Серверная поверхность

`custdev_cards` регистрируется в `schema-registry.js` **только на чтение** (доска и
отчёт), с embed-ами `patients`, `registrar`, `cashier`, `doctor`. Три embed-а в одну
таблицу `users` компилятор поддерживает: поиск в реестре идёт по имени отношения, а
JOIN всегда алиасится (`query-compiler.js`, parseColumns).

Записи — только через RPC, роли `['admin','callcenter']`, проверка `hasAnyRole`
(не `user.role`: у сотрудника роль может быть дополнительной, `extra_roles`) — тот же
гард, что в `server/services/rpc/crm-config.js`.

Раскладка файлов повторяет свежий образец `crm-config`: тонкий вход
`server/services/rpc/custdev.js` (разбор аргументов и гарды ролей) и логика в
`server/services/custdev/` — `sync.js` (создание карточек) и `score.js` (правило
вывода статуса). `score.js` при этом чистый и без обращений к базе, поэтому вся
таблица комбинаций проверяется тестом напрямую, без фикстуры.

| RPC | Аргументы | Делает |
|---|---|---|
| `custdev_sync` | `{ from, to }` | Создаёт недостающие карточки. Возвращает `{ created }`. |
| `custdev_rate` | `{ card_id, registrar, cashier, doctor, comment }` | Проверяет правила, выводит статус, штампует «кто и когда звонил». |
| `custdev_mark` | `{ card_id, status }` — только `new` или `unreachable` | Ручные статусы. Оценки при этом не трогает. |
| `custdev_report` | `{ from, to }` | Агрегаты периода (см. ниже). |

## Экран

Новый файл `public/js/admin/views/custdev.js`, экспорт `openCustDev()`.
`public/js/admin/views/crm.js` — уже 1433 строки — получает только кнопку рядом с
«Канбан» и один импорт.

**Кнопка «Cust Dev»** видна только владельцу и колл-центру. Иконка из
`icons.js`, без эмодзи.

**Рабочее место** — модальное окно во весь экран:

- шапка: «Cust Dev · Обзвон пациентов», крестик;
- панель: поиск по имени и телефону, чипы периода (Сегодня · Эта неделя · 30 дней ·
  Свой период — по **дате визита**), кнопки «Отчёт» и «Excel». Период по умолчанию —
  **30 дней**: «Сегодня» на этой доске всегда пусто (карточка появляется на следующий
  день), и пустой экран при открытии читался бы как поломка. Карточек читается не
  более **1000** за раз, как 800 заявок в CRM;
- доска из пяти колонок со счётчиками, постраничной дорисовкой и той же механикой
  перетаскивания, что в CRM (pointer-события), но разрешённой только между двумя
  ручными колонками.

**Карточка**: ФИО пациента, MRN, дата визита, телефон, сумма оплаты, имена
регистратора / кассира / врача, три компактных тега с текущими оценками.

**Попап оценки** (по клику на карточку): три сегментированных переключателя
«Доволен / Не доволен / Не применимо», поле комментария (обязательное, когда есть
«Не доволен» — кнопка сохранения до этого заблокирована с пояснением), кнопки
«Сохранить» и «Не дозвонились».

**Отчёт** за период: всего карточек, сколько **обзвонено** (доля карточек в статусе,
отличном от `new` — «Не дозвонились» считается попыткой и в обзвон входит), разбивка
доволен / частично / недоволен, и три таблицы — **по врачам, по кассирам, по
регистраторам** — со столбцами «доволен», «не доволен», «% довольных». В таблицах
учитываются только карточки, где этот критерий получил оценку `good` или `bad`:
`na` и `unrated` не попадают ни в числитель, ни в знаменатель. Считается
`custdev_report` по местным суткам (`inLocalRange`), как `callcenter_report`, роли
те же — `['admin','callcenter']`.

**Excel**: клиентская выгрузка через вендоренный SheetJS, как `exportExcel()` в CRM.
Лист «Cust Dev», колонки: Пациент · MRN · Дата визита · Телефон · Сумма ·
Регистратор · Кассир · Врач · Регистратура · Касса · Врач (оценка) · Статус ·
Комментарий · Кто звонил · Когда.

## Лицензирование и роли

Отдельный лицензируемый модуль **не заводится**: Cust Dev живёт внутри уже
существующего модуля `crm` и его гейта. Нового ключа в `NAV_MODULES` тоже нет —
это не пункт меню, а кнопка внутри экрана; доступ решается ролью на сервере
(`schema-registry` + гарды RPC), а клиент лишь прячет кнопку.

## Чего в первой версии нет

- Счётчик попыток дозвона и история звонков по карточке — статуса «Не дозвонились»
  на первое время достаточно.
- Отметка «жалоба разобрана» для руководителя.
- Автодозвон и связь с телефонией (Binotel, миграция 076).
- Настраиваемая задержка обзвона: «на следующий день» зашито константой.

## Тесты

- `server/db/migrations/078.test.js` — форма таблицы, CHECK-и, `UNIQUE(visit_id)`.
- `server/services/custdev/score.test.js` — **вся таблица вывода статуса**, все
  комбинации трёх оценок, включая «Не применимо». Чистая функция, без базы.
- `server/services/rpc/custdev.test.js` — идемпотентность `custdev_sync`; правило
  «следующий день» (визит сегодня карточку не создаёт); снимок сотрудников, включая
  откат врача на `visit_services`; что `custdev_rate` кладёт в базу статус, который
  вернул `score.js`; отказ при пустом комментарии и при трёх «Не применимо»; отказ
  ролям `registrar` и `doctor`.
- Гард реестра — запись в `custdev_cards` через `/api/db` отвергается.
- `custdev_report` — проценты на пустом периоде не делят на ноль.

## Риски

1. **Первый прогон в работающей клинике** создаст карточки за 90 дней разом. Это
   осознанно, но владельца надо предупредить: доска откроется с сотнями «Не обзвонён».
2. `paid_amount` — снимок. Возврат платежа после создания карточки сумму на карточке
   не изменит. Для опроса это неважно, для денег карточка не источник истины.
