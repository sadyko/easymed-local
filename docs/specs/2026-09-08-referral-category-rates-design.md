# Ставки вознаграждения живут на категории и на источнике — дизайн

**Статус:** реализовано 2026-09-08, ждёт проверки владельцем на дев-сервере
(раздел «Что выяснилось при реализации» — про три места, где спецификация
оказалась неправа)
**Решение владельца:** стандартная ставка задаётся В КАТЕГОРИИ источника;
источник либо берёт её («по категории»), либо задаёт свою целиком; строка
группы услуг может быть процентом ИЛИ фиксированной суммой

---

## Что решает

Сегодня, чтобы задать процент вознаграждения категории «Внешный врач», в
клинике заводят **правило вознаграждения с точно таким же названием**. Отчёт
«Рефералы» ищет ставку по СОВПАДЕНИЮ СТРОК: сначала правило с именем источника
(режим «Вручную»), потом правило с именем его категории (режим «Общий»), иначе
0% (`server/services/rpc/reports.js`, `referralsReport`).

Из этого следует всё остальное:

- опечатка в названии («Внешный» против «Внешний») молча превращается в 0% —
  никакой ошибки не показывается, партнёру просто не платят;
- ставка одна на всю категорию: лаборатории и хирургии нельзя дать разный
  процент, хотя маржа у них разная;
- фиксированную сумму за услугу («60 000 сум за снимок») задать нельзя вовсе —
  правило хранит только процент;
- чтобы понять, откуда взялась цифра в отчёте, надо открыть три экрана и
  сравнить названия глазами.

## Что есть сегодня — три механизма, живой один

Разбор кода 2026-09-07. Это важно записать: два из трёх выглядят рабочими с
экрана настроек, но не участвуют в расчёте.

| Механизм | Где | Состояние |

| `companies.referral_reward_rates` — % по группам на всю клинику | Меню → экран «Реферальное вознаграждение» (`views/referral-settings.js`) | **Сломан.** Колонки нет ни в одной миграции и нет в реестре — экран умеет показать только предупреждение «примените миграцию 103» |
| `referral_sources.commission_mode` / `commission_rates` | `views/reports-export.js`, `buildReferralReport` | **Сломан, но ЖИВОЙ** — см. «Что выяснилось при реализации» |

Второй и третий — наследство облачной версии на Supabase. Их писали под ту же
задачу, что решается здесь, и ни один не довели до расчёта.

## Решения владельца

Приняты 2026-09-08. Каждое меняет объём, поэтому записаны дословно по смыслу.

1. **Убрать оба старых экрана.** Ставки живут только на категории (стандартный
   процент + строки по группам) и на источнике (своя ставка). Плитка
   «Реферальное вознаграждение» и сломанный общеклинический экран уходят из
   меню. Одно место, куда смотреть, когда деньги посчитались не так.
2. **Категория у источника — выпадающий список, а не свободный текст.**
   Настоящая внешняя связь. Опечатка больше не может стоить партнёру ставки.
3. **Источник в режиме «своя ставка» не смотрит на категорию вообще.** Пустая
   строка группы → «свой процент» → 0. Карточка источника объясняет его выплату
   целиком, без второго экрана.
4. **Фиксированная сумма умножается на количество.** Строка «3 снимка по
   60 000» даёт 180 000. Так же ведёт себя процент: он и сейчас берётся от
   суммы строки, а в ней количество уже учтено.

## Три решения, принятые без вопроса

Записаны отдельно, потому что владелец их не выбирал — если какое-то не то, оно
переигрывается до реализации.

1. **Вознаграждение считается ПОСЛЕ скидки** (`amount − discount`) — ровно как
   сегодня в `referralsReport`. Партнёр получает долю того, что клиника
   действительно взяла с пациента, а не прайсовой цены.
2. **Кнопки «Удалить» не будет.** На макете источника она есть, но реестр
   обоим таблицам ставит `delete:{roles:[]}` намеренно: удалённый источник
   осиротит визиты и счета, которые на него ссылаются. Источник выводят из
   оборота галочкой «Active».
3. **JSON ставок не проверяется на сервере по форме.** Писать эти колонки может
   только `admin`, а читатель отчёта defensive: нечисловые и отрицательные
   значения игнорируются, неизвестные `type_id` пропускаются. Настоящий
   валидатор формы означал бы правку ядра — модуля разрешений
   `schema-registry.js`, — и ради этой задачи туда лезть не стоит.

## Модель данных — миграция `109_referral_category_rates.sql`

Следующий свободный номер: старший существующий — `108_rooms_wards_department.sql`.

```sql
ALTER TABLE referral_source_categories ADD COLUMN standard_percent REAL NOT NULL DEFAULT 0;
ALTER TABLE referral_source_categories ADD COLUMN rates            TEXT NOT NULL DEFAULT '';

ALTER TABLE referral_sources ADD COLUMN category_id INTEGER REFERENCES referral_source_categories(id);
ALTER TABLE referral_sources ADD COLUMN reward_mode TEXT NOT NULL DEFAULT 'category';
ALTER TABLE referral_sources ADD COLUMN own_percent REAL NOT NULL DEFAULT 0;
ALTER TABLE referral_sources ADD COLUMN own_rates   TEXT NOT NULL DEFAULT '';
```

`reward_mode` — `'category'` (галочка «Вознаграждение по категории» стоит) либо
`'own'`. По умолчанию `'category'`: новый источник наследует ставку категории,
это обычный случай. **CHECK намеренно не ставится** — тем же доводом, что в
миграции 058 для `payment_type`: упавший CHECK на живом регистре хуже
неожиданной строки, а читатель ставок неизвестный режим трактует как `'category'`.

### Форма JSON

`rates` и `own_rates` — массив, по записи на настроенную группу услуг:

```json
[{"type_id": 3, "unit": "pct", "value": 10},
 {"type_id": 7, "unit": "fix", "value": 60000}]
```

Массив, а не объект-карта, — по образцу `users.referral_rates` (миграция 021),
единственного уже существующего в проекте хранилища ставок. Ненастроенной группы
в массиве просто нет; пустая строка формы запись не создаёт.

В реестре колонки объявляются как JSON (`json:['rates']`, `json:['own_rates']`) —
компилятор сам сериализует объект на запись, маршрут сам разбирает на чтение
(`server/db/query-compiler.js`, `bindWrite` и `meta.json`). Новой прокладки не
требуется.

### Правки реестра `server/db/schema-registry.js`

- `referral_source_categories`: `standard_percent`, `rates` в `read`, `insert`,
  `update`; `json:['rates']`.
- `referral_sources`: `category_id`, `reward_mode`, `own_percent`, `own_rates`
  в `read`, `insert`, `update`; `json:['own_rates']`; `filters` пополняются
  `category_id`; появляется вложение
  `embed:{ referral_source_categories: { table:'referral_source_categories',
  fk:'category_id', columns:['id','name'] } }` — список источников в настройках
  печатает название категории через него.

Инвариант не затрагивается: JSON уходит в базу связанным параметром TEXT,
идентификаторы по-прежнему сверяются с реестром.

## Перенос существующих настроек

Это часть, которую нельзя сделать неправильно: после обновления клиника должна
получить ТЕ ЖЕ суммы, что считались накануне. Три шага в одной миграции, по
порядку.

**Шаг 1. `category_id` из свободного текста.** Каждое непустое значение
`referral_sources.category` сверяется с `referral_source_categories.name` без
учёта регистра и пробелов по краям. Не нашлось — категория создаётся. Затем у
всех связанных строк `category` обнуляется в `''`, чтобы источник правды остался
один и рядом не лежала строка, которую следующий читатель примет за настоящую.

Оговорка, которую нужно знать заранее: если в регистре сегодня есть и «Внешный
врач», и «Внешний врач», получатся ДВЕ категории. Миграция сохраняет то, что
есть, а не угадывает, где опечатка; свести их вручную — минутное дело, а
угаданное слияние ставок необратимо.

**Шаг 2. Активные правила с именем категории → `standard_percent` этой
категории.**

**Шаг 3. Активные правила с именем источника → `reward_mode='own'` и
`own_percent` этого источника.**

Оба шага берут только `referral_rewards.active = 1` — ровно то, что читает
сегодняшний отчёт; выключенное правило не платило вчера и не должно начать
платить после обновления. Сопоставление — без учёта регистра и пробелов по
краям, как в `referralsReport`. Если под одно имя подходят несколько правил,
берётся правило с наибольшим `id`: сегодняшняя `Map` строится обходом списка и
последнее совпадение затирает предыдущие, а список приходит в порядке вставки.

Порядок шагов 2 и 3 повторяет порядок разрешения в сегодняшнем
`referralsReport` (правило по имени источника перекрывает правило по имени
категории), поэтому первая же выгрузка отчёта после обновления даёт прежние
цифры.

Таблица `referral_rewards` остаётся в базе со всеми своими строками — миграции
здесь ничего не роняют, — но после шага 3 её никто не читает. Это и есть путь
назад, если перенос окажется неверным: исходные правила лежат нетронутыми.

## Расчёт — `public/js/shared/referral-reward.js`

Один модуль, одна таблица истинности. Экспортирует
`resolveReferralRate({ source, category, serviceTypeId })` → `{ unit, value }`
и `rewardForLine(rate, { amount, discount, qty })` → число.

```
режим 'category':  ставка группы у категории → стандартный процент категории → 0
режим 'own':       ставка группы у источника → свой процент источника        → 0
```

В режиме `'own'` категория не читается ни при каких условиях — решение
владельца 3. У источника без категории в режиме `'category'` вознаграждение 0.

```
unit 'pct'  →  (amount − discount) × value / 100
unit 'fix'  →  value × qty
```

Читатель терпимый: запись без числового `value`, с отрицательным `value`, с
неизвестным `unit` или ссылающаяся на несуществующую группу — пропускается, как
если бы её не было. Испорченный JSON целиком читается как пустой массив.

## Отчёт «Рефералы»

`server/services/rpc/reports.js`.

- `itemRowsQuery` добирает `s.type_id AS service_type_id` и `rs.id AS
  referral_source_id` (соединение с `services` и `referral_sources` там уже
  есть). `rs.category` уступает место `rc.name` через новое соединение с
  `referral_source_categories`.
- `referralsReport` группирует по `referral_source_id`, а не по строке имени:
  ставка теперь зависит от источника, а два партнёра-однофамильца больше не
  сложатся в одну строку. Для строк, чей источник удалён из базы, ключом
  остаётся имя.
- Вознаграждение накапливается ПО ПОЗИЦИЯМ: у одного источника в одной корзине
  теперь может быть шесть разных ставок.
- Колонка «% вознаграждения» больше не может держать одно число и заменяется на
  **«Эфф. %»** = `reward_sum / amount_sum × 100`, при нулевой сумме услуг — 0.
  Это всегда верная цифра — та самая, которую в отчёте ищут глазами, — и она
  честно показывает смесь процентов с фиксированными суммами.
- Колонка «Режим ставок» сохраняется: «По категории» / «Своя».

## Экран категории (макет 2)

`public/js/admin/views/settings-hub.js`, конфигурация
`referral_source_categories`. Поля:

- `name` — как есть;
- `standard_percent` — число, подпись «Стандартный процент — со всех услуг,
  кроме перечисленных ниже»;
- `rates` — новый тип поля `group_rates`;
- «Active» — уже есть на редактировании.

`modalWidth: '760px'`.

### Новый тип поля `group_rates`

Занимает всю ширину модалки (обе колонки сетки). Таблица: строка на каждую
активную запись `service_types` (`active=1`, по названию), в строке — числовой
ввод и выпадающий список единицы «%» / «сум». Подпись под заголовком: «Пусто —
действует стандартный процент сверху. Заполненная строка его перекрывает: % —
доля от стоимости услуги, сум — фиксированная сумма за услугу.»

Группы услуг грузятся после монтирования модалки, как это уже делают `fk` и
`suggest` поля: модалка открывается сразу, таблица дозаполняется.

`.value` геттер собирает массив описанной выше формы, пропуская пустые и
нечисловые строки, — обобщённый `save()` в `settings-hub.js` берёт значение
через `.value` и ничего про новый тип не знает.

## Экран источника (макет 4)

Та же конфигурация, `referral_sources`. Поверх сегодняшних полей ФИО, телефона,
места работы, района и реквизитов выплаты:

- `category_id` — тип `fk` вместо `suggest`, таблица
  `referral_source_categories`, подпись «Категория»;
- `reward_mode` — новый тип поля `checkbox` с подписью «Вознаграждение по
  категории (общая ставка)», по умолчанию установлена; хранит `'category'`,
  когда стоит, и `'own'`, когда снята;
- `own_percent` — число, «Свой процент — со всех услуг, кроме перечисленных
  ниже»;
- `own_rates` — второй `group_rates`, «Свои ставки по группам услуг».

Последние два скрыты, пока галочка стоит.

`modalWidth: '820px'`, сетка в две колонки сохраняется; обе таблицы ставок
занимают полную ширину.

### Две небольшие правки модалки настроек

Обе — в общий механизм, обе нужны этой форме:

1. **`visibleWhen`** — поле показывается по состоянию другого поля. Такое уже
   есть в `public/js/admin/sections.js` (`visibleWhen: (v) => v.commission_mode
   === 'manual'`), в `settings-hub.js` нет; переносится с той же семантикой,
   пересчёт по `change` на управляющем контроле.
2. **Тип поля `checkbox`** — галочка, хранящая одно из двух значений
   перечисления (`checkedValue` / `uncheckedValue`), а не 0/1.

## Что НЕ входит

- начисление вознаграждения в момент оказания услуги и его хранение в базе:
  расчёт остаётся отчётным, как сегодня;

## Что выяснилось при реализации

Три утверждения спецификации оказались неверны. Записано здесь, а не молча
исправлено в коде: следующий читатель имеет право знать, что разбор перед
работой ошибся, и в чём именно.

**1. `buildReferralReport` — не мёртвый код.** Спецификация объявила его
мёртвым, потому что поиск по имени функции ничего не нашёл за пределами
собственного файла. Он и не должен был найти: функция зарегистрирована в
таблице отчётов ВНУТРИ того же файла (`REPORTS`), а таблицу экспортирует
`renderDownloadsPanel`, которую грузит `views/reports.js`. То есть это живая
выгрузка на экране «Отчёты», и она была сломана — читала колонки
`commission_mode` / `commission_rates`, которых в этой базе нет, и падала с
советом «примените миграцию 103».

Поэтому её не удалили, а переписали на новую модель. Отсюда же следует, что
отчёт «Рефералы» существует ДВАЖДЫ — на сервере и выгрузкой в браузере, — и
модуль выбора ставки переехал в `public/js/shared/`, общий для обоих: две копии
правила «какая ставка применяется» означали бы две разные суммы к выплате. Тот
же приём, что у `shared/payment-methods.js`.

**2. Встроенный `lower()` в SQLite складывает регистр только у латиницы.**
Перенос сравнивает названия без учёта регистра, и на «Внешний»/«внешний» он бы
молча не сработал — а отчёт, который переносится, сравнивает имена
джаваскриптовым `toLowerCase()`, который кириллицу складывает. Разошедшееся
сравнение означало бы, что после обновления партнёру платят другую сумму.
В проекте для ровно этого случая уже есть UDF `lower_uni`
(`CYRILLIC_ILIKE_V1`, `db/connection.js`) — миграция пользуется им.

**3. Атрибут `hidden` не прятал поле.** `.field { display: flex }` в
`admin.css` перебивает `[hidden]` из браузерной таблицы стилей, поэтому
`el.hidden = true` оставлял «свои ставки» на экране при поставленной галочке.
Добавлено правило `.field[hidden] { display: none !important; }` — тем же
приёмом, что уже применён к `.user-popover[hidden]` и `.appbar-back[hidden]`.

Отдельно, из проверок: `Number(null) === 0`, поэтому запись ставки без значения
читалась как честно выставленный «0%» и перекрывала процент уровнем выше —
партнёр получал ноль там, где должен был получить стандартный процент. Пустота
теперь отсеивается ДО `Number()`, а явный ноль остаётся полноценной ставкой
(«за эту группу не платим»).
