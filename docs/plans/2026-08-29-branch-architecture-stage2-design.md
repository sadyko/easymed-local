# Branches as real installs: identity, patient numbers, and two-way sync

Design settled with the owner on 2026-08-29. This supersedes the "Stage 2" and
"Stage 3" sketches in `2026-08-29-branch-sync-DESIGN-QUESTION.md`, which said
only *what* was deferred, not *how* it would work. Stage 1 (catalogue, one-way)
is built and unchanged; this document is what comes after it.

Nothing here is implemented yet.

## What the owner asked for, in his words

> «the main branch is where key activated. the other branches are: where in the
> activation process key of the branch (generated by admin in the clinic) is
> inputted. in the branch list should be only the branch name. and activation
> key (not one time generated). system should get its patients, lab or any other
> information based off a synchronization, to avoid the id collapse of the
> patients we need to make sure that id generated for the patient is unique. but
> not too long so we can identify. also the reports etc.»

Four decisions were then taken explicitly, each recorded below with the reason
the alternative was rejected. They are written down because in a year the
question will not be "what did we build" — it will be "why", and a medical
system that cannot answer that has a real problem.

---

## 1. Branch identity and activation

**One licence per clinic, held by the main branch.** Secondary branches do not
enrol with settings.easymed.uz and do not consume a separate subscription. They
join the clinic, not the vendor.

```
MAIN branch                          SECONDARY branch
licence activated with EM-xxxx       branch key entered during setup
   |                                        ^
   |  branch key, generated by the          |
   +--  clinic's own admin  ----------------+
```

**The branch key is permanent, not one-time.** `Настройки → Филиалы` lists every
branch as *name + its activation key*, always readable.

This is a deliberate reversal of Stage 1's pairing key, which was issued once and
then hidden. The reason is operational, not cryptographic: a branch PC gets
reinstalled, or replaced after a failure, and at that moment a one-time code that
nobody wrote down turns a ten-minute job into a support call to the vendor. A key
the clinic can always read off its own screen removes that call entirely.

The cost is honest and accepted: anyone who can see the branch list can add a
branch. That list is already behind an admin role, and the threat it would defend
against — someone with admin access to the clinic's own system — is not a threat
this key can meaningfully stop anyway.

**Re-issuing a key** un-pairs every branch using it, and the screen must say so
before doing it, not after.

**The branch letter** (the `A` in `A-26-00042`) is assigned by the main branch
when the branch is created, stored on the `branches` row, and never reused — not
even after a branch is closed. Reusing a letter would make two different people
share an MRN years apart, which is the one failure this scheme exists to prevent.
The main branch is `A`. Letters are allocated in order; past `Z` the scheme
continues `AA`, `AB`, and the format must not assume a single character.

## 2. Patient numbers: the MRN becomes the identity

The row id (`patients.id`, `INTEGER PRIMARY KEY AUTOINCREMENT`) is unusable across
installs and always will be: every branch independently allocates 1, 2, 3. Two
branches syncing on row id would merge two unrelated people on their first day.

The system already has the right identifier and has had it since migration 002:
`patients.mrn`, `TEXT UNIQUE`, auto-generated as `P-26-00042` and already printed
on documents. It gains a branch letter:

```
A-26-00042     branch A, registered 2026, number 42
B-26-00042     a completely different person
```

Short enough to read down a phone line, unique across every branch forever, and
it carries where the patient was first registered — which is exactly the question
staff ask when two records look similar.

**Row ids stay local and are remapped on arrival.** This is not a new mechanism:
`server/services/branch-sync/catalogue.js` already matches incoming rows by their
natural key and rewrites foreign keys to local ids (`refs`, `natural`, and the
two-pass `selfRef` handling for self-referencing tables). Patients extend that
pattern with `natural: ['mrn']`. Every table that points at a patient is remapped
the same way.

**Existing patients keep their current MRNs.** Roughly 70,000 rows are already
numbered without a branch letter, and many are printed on cards patients carry.
Renumbering them would invalidate physical documents to gain nothing: they are
already unique inside their own install, and the branch letter only has to make
*future* numbers distinguishable. Only new patients get lettered. The matcher
must therefore accept both shapes, and a test must pin that an unlettered MRN
still round-trips.

**Same person, two branches, two numbers.** If someone registers separately at A
and at B before the branches ever sync, they will hold two MRNs. That is not a
bug to be prevented — it is a duplicate that has to be *found*, using the same
duplicate detection the system already has for one install (name + date of birth
+ phone). Merging two MRNs into one is a separate, later, deliberately manual
feature. Automatic merging of medical records on a name match is not something
this system should ever do.

## 3. What travels, and who may change it

**Everything travels, both directions:** patients, visits, lab orders and
results, documents, invoices, payments, and the catalogue that Stage 1 already
carries.

**Permission is by role, never by geography.** The owner was explicit: «any
branch, based off a permission levels of the roles». Being physically at another
branch grants no extra rights and removes none. A user who may edit a patient may
edit that patient anywhere; a user who may not, may not, at home or away. This
keeps one permission model instead of two, and the existing role checks apply
unchanged.

### Conflict rule: newest wins, field by field

Chosen over whole-record replacement, which was rejected for a specific reason:
it destroys work that never conflicted.

```
A: phone   -> 90-123-4567   10:02      A: phone -> 90-123-4567   10:02
B: address -> Chilanzar 5   10:05      B: phone -> 91-765-4321   10:05

both survive; they never collided      B wins (newer). A's value is kept
                                       in history and shown on screen
```

Requirements this places on the implementation:

- every synced table needs a per-field `updated_at`, or a per-row change log
  carrying which fields changed and when. A single row-level `updated_at` is not
  enough to merge field by field.
- clocks. Two PCs disagreeing by minutes will resolve conflicts wrongly and
  silently. Stage 1 already refuses a sync on clock skew and reports it as its
  own distinct reason rather than as a bad key; that guard must extend here.
- the replaced value is never discarded. "Newest wins" is only acceptable
  because the loser stays visible.

### Money is appended, never overwritten

The owner chose «fully editable based off a permission of the role» for invoices
and payments. That permission model is kept exactly. What changes is the storage
model, because field-level last-write-wins on money is unsafe in a way a phone
number is not:

> Two branches take a payment on the same invoice while disconnected. Under
> last-write-wins the newer payment overwrites the older. That is not a lost
> keystroke — it is a payment the clinic received and can no longer see.

So:

- **a payment is an event, not a field.** Two branches each add one; both
  survive; nothing is overwritten; the total is right.
- **a correction is a new entry** (a reversal), never an edit of the original —
  which is how accounting works anyway, and leaves an audit trail for free.
- **invoice totals are derived** from lines and payments, not stored as an
  editable number that two branches could each set to a different value.

Anyone whose role permits it can still take payment at any branch. Nothing is
forbidden that was allowed. The only thing removed is the ability to silently
destroy a record of money.

## 4. Transport: patient data may use the encrypted relay

**Decision, 2026-08-29:** patient data uses whichever route works — direct when
the branches can reach each other, and the encrypted relay through
settings.easymed.uz when they cannot. The owner chose this over an opt-in switch,
having been shown that the alternative was a clinic whose distant branches simply
would not sync.

**This supersedes the founding constraint of the control plane**, stated at the
start of the project and honoured by everything built until now:

> statistics and subscription control live at settings.easymed.uz — but
> **«NOT PERSONAL DATA OF THE PATIENTS»**

It is superseded in *letter*, not in substance, and the distinction is the whole
justification: the relay stores AES-256-GCM ciphertext whose key is generated at
activation, lives only on the clinic's own machines, and travels between branches
only inside the hand-carried branch key. The vendor holds bytes it cannot read
and has no mechanism to read. `relay.route.test.js` proves this by seeding a
marker into a clinic database and asserting it is absent from what the server
stores.

**An unresolved consequence, found while reviewing this document.** Section 1
says a secondary branch does not enrol with settings.easymed.uz — it joins the
clinic, not the vendor. But Route B's relay route authenticates a caller by its
*install token*, which only enrolment produces. A secondary branch therefore has
no credential the relay will accept, and as written could not use the fallback
route at all.

The intended resolution is that the branch key itself carries what is needed to
reach the relay, so the credential arrives from the clinic's own main branch
rather than from the vendor. That keeps "one licence per clinic" intact while
letting every branch use the relay. It has to be designed properly at Stage 1 of
the build order below, because it changes the shape of the branch key, and the
branch key is the first thing built. Flagged here rather than discovered later.

What genuinely changes, and must not be glossed:

- encrypted patient records now rest on vendor-controlled disks. Legally that is
  a different position from holding nothing, whatever the encryption.
- a clinic that loses its key loses that data, and the vendor cannot help. This
  is already true of the catalogue and is written into the UI; with patient data
  behind it the sentence carries far more weight and must appear where a clinic
  will actually read it, not only in a settings screen nobody opens.
- retention on the relay must be bounded, and deleting a clinic must delete its
  blobs.

---

## 5. Reports

Per branch and clinic-wide, from the same synced data, with each invoice counted
exactly once — which the append-only money model guarantees structurally rather
than by careful summing.

Nothing here is hard once the data is present. Reporting was never the difficult
part; sharing the data correctly is.

---

## 6. Order of building

Each stage ships and runs in a real clinic before the next begins.

1. **Branch identity** — permanent branch keys, the branch list, activation by
   branch key. No clinical data moves yet. Small, and it de-risks everything
   after it.
2. **Patients** — lettered MRNs, matching, field-level merge, the conflict
   history view, clock-skew refusal. The hardest correctness work.
3. **Visits, lab orders and results, documents** — append-shaped and therefore
   easier, but only once patient identity is proven in a real clinic.
4. **Money** — last, on the append-only model, with the heaviest testing. A bug
   here is somebody's revenue.
5. **Reports** — combined and per-branch.

## Risks worth stating plainly

- **This is weeks of work, not a session**, and the failure modes are the
  expensive kind: a lab result attached to the wrong patient, a payment that
  disappears, two records for one person. Every stage above exists to make those
  findable in a small blast radius rather than all at once.
- **No amount of testing substitutes for one real clinic with two real branches.**
  Stage 1 is already built and, at the time of writing, no human has yet clicked
  it. That should change before Stage 2 begins.
- **Clock skew is the quiet one.** Everything about "newest wins" rests on two
  clinic PCs agreeing what time it is, and nothing about a clinic PC guarantees
  that.
