## 1. Booking gaps — one packing rule

**Cause.** `server/services/rpc/slot-engine.js` `slotStarts()` (240–254) walks a fixed step from the
start of each working segment and drops starts that overlap a booking. It never adds a start at the end
of a booking. Each screen also sends its own step:

| Screen | Step today |
|---|---|
| CRM «Даты приёма» (`crm.js` 2973 → `loadSlotDay`, `SLOT_STEP_MIN = 30` in `service-picker-modal.js` 3742) | 30 |
| Visit wizard (`visit-wizard.js` 1604, 1622, 1692) | 30 |
| Calculator catalog (`service-picker-modal.js` 1831, 1857) | 30 |
| Picker schedule strip (`SCHED_SNAP = 15`, `service-picker-modal.js` 1151–1400) | 15 |
| Doctor cabinet «Повторный визит» (`RV_SLOT_MIN = 20`, `service-workspace.js` 1623) | 20 |
| Server `calendar_slots` without a step (`calendar.js` 849) | = duration, from the segment start |

The server already accepts back-to-back (touching ends are not an overlap): booking 10:40 after
10:10–10:40 is accepted. Only the offered lists hide it.

Reproduction (doctor 09:00–18:00, bookings 09:00–09:30 and 10:10–10:40, 30-min service):
today `09:30, 11:00, 11:30…`; with packing `09:30, 10:40, 11:10, 11:40…`.
15-min service with packing: `09:30, 09:45, 10:40, 10:55…`.

**Fix.**
1. `slot-engine.js`: new `packedStarts({ segments, busy, durationMin, minStartMin })`:
   free gaps = working segments minus merged busy blocks; in each gap start at the gap's beginning
   and step by the service duration while the service fits. Today: first start = now rounded **up to
   5 minutes** (no «10:07»). Plus `startFits()` for validation.
2. `calendar.js` `calendarSlots` (849–869): no `step_minutes` → packed starts; an explicit step keeps
   the old grid (partner API keeps sending 15).
3. Clients stop sending fixed steps: `loadSlotDay`/`_slotKey` (`service-picker-modal.js` 3742–3777),
   `SCHED_SNAP` uses, `RV_SLOT_MIN`. `gateDaySlots` (`visit-wizard.js` 1692–1707) checks «fits»
   instead of «is in the list» (packed anchors move when someone else books).
4. Unsaved lines of the same estimate count as busy (`extra_busy`), so two new services for one
   doctor pack one after another.
5. Room calendar: its own grid step (5–60, user's choice) stays for drawing; «Записать» from a
   cell still accepts any minute (unchanged).

**Default (no question):** public online booking (Symptex / partner API, `PUBLIC_SLOT_MIN = 15`)
stays on its 15-minute grid — it is a published contract (`docs/specs/2026-10-11-clinic-api-8-public-server-design.md`
§191). Cost: up to 14 min gap after an off-grid internal booking. Packing there = a later, versioned
API change.

**Tests.** `slot-engine.test.js` (after a booking, after lunch, today's rounding, gap too small, mixed
durations); `calendar.test.js` (no step → packed; explicit step → grid); `calendar-holds.test.js`
(holds are busy); `bookings-*.test.js` (partner grid unchanged); `wizard-booking.test.mjs:401`,
`picker-one-instance.test.mjs:103`, `consultation-flags.test.mjs:485` (they assert the old steps);
new static check in `booking-doors.test.mjs`: no screen sends a fixed step to `calendar_slots`.

## 2. Join the existing booking; never move it silently

**Cause.** The join rule lives in the visit wizard (`visit-wizard.js` 1632–1655, 1739–1743) and the
calculator (`service-picker-modal.js` 1846–1855, 2069–2073) via `booked-rows.js` 124–170.
`crm.js` never uses it. The CRM window passes `patientId`, so the patient's own 10:10 booking is
removed from «busy» and, being off the 30-min grid, never offered. On save `bookDays`
(`crm.js` 3113–3129) calls `ensure_visit` with a booking; if that visit has no work yet,
`ensure_visit` **moves** it (`visits.js` 339–341, 368–397). Reproduced: `{"moved":true,"from":"10:10"}`,
visit now 09:30. The operator only sees a «перенесено» toast (`crm.js` 3187).

**Fix.**
1. `crm.js` `paintTime`: load the patient's bookings, add and **preselect** «в запись · 10:10»
   (string exists, `i18n-strings.js` 13625). A line on the join time calls `ensure_visit` without a
   booking (as `tests/crm-doors/booked-join.test.mjs` `wizardJoin`).
2. Server guard (`visits.js` ~339–397): same doctor, same day, before arrival, same start → join, no
   `calendar_book`.
3. Moving an existing booking to another time only through an explicit «Перенести запись на …»
   choice in the time list (shown under the join option), never as a side effect.
4. Visit wizard: a future-day click and «Ближайшее» prefer the join time (today they pick the earliest
   free start, `visit-wizard.js` 1483–1486).
5. **Default (no question):** a joined service lengthens the booking by its duration when the time
   after it is free; if the next booking starts sooner, the time list shows «приём закончится в
   10:55, следующая запись в 10:40» and the booking keeps its length.

**Tests.** `tests/crm-doors/booked-join.test.mjs` (CRM card joins, does not move);
`public/js/admin/__tests__/crm-card.test.mjs` (10:40 offered, join preselected);
`booked-join-wizard.test.mjs` (future day prefers join).

## 3. Lab analyses ask for a doctor

**Cause (reproduced, `repro-lab-calculator.test.mjs`).**
- Calculator catalog `service-picker-modal.js` 2036: `svc.requires_doctor === false` — `/api/db`
  returns SQLite `0`, so it is never true. «Нужен врач» then becomes «есть исполнитель»: one lab tech
  in «Услуги и ставки» → auto-assigned **with a time slot**; two lab techs → «выберите врача и время»,
  button disabled. A lab left in the default «Консультации» group → all doctors become candidates.
- The picker loads services with `select('*')` and ignores the lab hints (`ROUTE_SELECT`, 456).
- Room calendar, doctor column: the calculator is locked to that doctor and hides services the doctor
  does not perform (1808–1814); labs that show are booked into the doctor's time (2018–2029).
- Visit wizard: labs left in «Консультации» without a lab hint are routed to a doctor's office
  (`service-route.js` 125–129) — «Далее» blocked.
- CRM card: correct in code (only `requires_doctor` decides).

**Fix.** `needsDoc = !!svc.__consult || isOn(svc.requires_doctor)` (as the wizard does, 1271, 1724,
3242); performers of `requires_doctor = 0` services are picked without a time; services loaded with
`ROUTE_SELECT`; in a doctor-locked calculator, lab and procedure services that need no doctor are
offered as «на дату» lines (no doctor, no time).

**Clinic check (read-only, with the owner's permission, optional):** lab services with
`requires_doctor = 1` would also ask for a doctor in the CRM card — then it is a catalogue setting, and
«Справочник услуг» should say so.

**Tests.** `pick-day-calculator.test.mjs` (cases: lab group no performer; one lab tech; two lab techs;
«Консультации» group with one/two doctors); `room-calendar.test.mjs` (doctor column books a lab
without the doctor).

## 4. Registrar sees every booked line

**Cause.** `public/js/admin/crm-lines.js` `pendingCrmLines` (57–61) reads only open + conversion
columns, and reads through `/api/db`, where the CRM ownership limit applies
(`schema-registry.js` 62): a registrar sees only unassigned cards and their own. Reproduced:
card taken by an operator → registrar sees nothing, admin sees it. The server (`visit-link.js`
481–531) seats these lines anyway — the browser and the server disagree.

**Fix.** New RPC `crm_day_lines { patient_id, day, visit_id }` that reuses the server's own rule
(open + conversion + «Не пришёл» role, no ownership limit) and returns only service, doctor and date —
not the card's notes or phone history. `crm-lines.js` calls it instead of the two `/api/db` reads.

**Tests.** `crm-lines.test.mjs`, `service-picker-crm.test.mjs`, a server test for the RPC with a
registrar user and an operator-owned card.

## 5. New card jumps to «Пришёл» / «Не пришёл»

**Cause.** `ensure_visit` and `calendar_book` carry no card id. `crmLinkVisit` guesses the card(s) by
patient; `deskCloses` (`visit-link.js` 344–357, the `inWindowSql` clause at 353) and `settleLineless`
(`visit-status.js` 150–164, clause at 158) treat any card moved in the last 72 h as «the same request»
— a new card always qualifies. Reproduced (`repro-item2c.mjs`):

| Case | Result today |
|---|---|
| P1: new card B booked for +3 days; today the patient is registered at the desk for old card A | A = Пришёл, **B = Пришёл** (its +3 booking still pending) |
| P3: B created while the patient is here on A's visit; A marked «Пришёл»; then B booked for +3 | **B = Пришёл**, and B's new booking is linked to no card |
| P4: B has an undated lab; the registrar opens A's visit; A marked «Не пришёл» | A = Не пришёл, **B = Не пришёл** |
| Mirror: A in «Не пришёл» (<72 h), new booking on B | **A dragged** to «Записан», then follows B's visit |

**Fix.**
- F1 — the booking names its card: `bookDays` sends `crm_request_id`; `ensure_visit` /
  `calendar_book` pass it to `crmLinkVisit({ requestId })`; then only that card's lines are seated,
  linked and moved (steps C, C′, D, E skipped).
- F2 — a card that holds its own live booking on another day is never closed by another visit
  (`deskCloses`, `waitsForDay`).
- F3 — `settleLineless` never closes a card created after the arriving visit was created.
- F4 — calendar bookings without a card id take **one** card (the most recently moved live card), not
  every matching card; a wish pulled into another card's visit does not move its own card.
- These replace the earlier «72 h window = same request» rule for these cases (owner's report of
  2026-11-10 is the evidence that rule now does harm). The 72 h window still merges a repeat *call*
  into the existing card.

**Tests.** `visit-link.test.js`, `visit-status.test.js`, `no-show.test.js`, `contact-window.test.js`,
`crm-unify-desk.test.js`, `crm-link-all-live-card.test.js`, `crm-calendar-mirror.test.js`, plus a new
door test porting P1/P3/P4/mirror. Existing tests that assert the window behaviour get new expectations.

## 7. CRM filter bar

**Cause.** Search (name, phone in any format) and «Оператор» work. «Период»:
`crm.js` 231–237 (`inPeriod` returns true for every open card) and `crm-board-load.js` 81–83 (open
cards load with no date limit) — by design since 3.17 (CRM_UNIFY_V1). With 6 800 open cards,
«Сегодня» still shows 6 800 (6 782 of them older than today). «Источник»: the «Все» option has an
empty value (`crm.js` 948), which `ui-select.js` 92 draws grey as a blank and leaves out of the list —
the filter works but looks switched off. «· 7163» counts loaded cards, not sources, and doesn't match
the column numbers.

**Fix (decided, Q1).** A chosen period filters every column by the date the card came in;
above the board: «Период «Сегодня»: показаны заявки, поступившие сегодня. Открытых за другие дни: N —
Показать все». «Всё время» stays the default. «Все» gets a real value, dark text, listed; the number
becomes the sum of the visible columns (or is dropped). Chips show «загрузка» while the board reloads;
custom «по» date includes the whole last day.

**Tests.** `crm-board-columns.test.mjs` (C3 asserts the old rule — rewrite), `crm-board-load.test.mjs`,
`crm-multi-source.test.mjs`, `crm-tags.test.mjs` (with the real `enhanceSelect`), i18n leak tests.

## 8. «Изменить скидку» after payment

**Today.** `cashier_invoice_discount` (`billing.js` 3236–3319) only adds a discount, only while nothing
is paid (3258–3261). A 100 % discount closes the invoice at once (`settleZeroTotal`) — no «Скидка»
button, no «Платежи» window. Reproduced: 409 «Скидку дают до оплаты». The only workaround today is a
partial refund, which reports treat as returned money (doctor share always cut, partner bonus cut).

**Fix.** New RPCs `cashier_invoice_discount_change` + `_quote`, modelled on `swapPaidLineTx`
(«Заменить услугу», `billing.js` 2117–2365): reprice the invoice-level discount (0 allowed = remove),
reason required, «уменьшает долю врача» switch; recompute the invoice; then
- new total **below** what was paid → return the difference (as in «Заменить услугу»);
- new total **above** → «К доплате N», invoice becomes partly paid / debt;
- cashback rolled back or credited, audit entry, refunds list shows «Изменение скидки»,
  closed pay month refused (as service swaps), receipt slip «Изменение скидки».
Entry points: «Платежи» window; «Изменить скидку» in the row of a 100 % invoice; the pay dialog of a
partly paid invoice; the total line of «Исправить услуги».
Discounts that belong to lines (package, per-service rates like «Сотрудники: консультация 100 %») are
not changed by this; the dialog says so.

Worked example (200 000, 20 % paid = 160 000 → change to 50 %): new total 100 000, return 60 000.
Doctor share (30 %, switch on) 48 000 → 30 000. Partner bonus (10 %, full-price rule) stays 20 000.
Reverse (100 % → 0 % on 200 000): patient owes 200 000, invoice «не оплачен»/долг; started work stays.

**Decided (Q2–Q4, 2026-11-10):** raise and lower, 100 % included; the cashier chooses cash-back or
balance each time; allowed to whoever has «Кассир может давать скидку», plus admins.

**Tests.** New `cashier-discount-change.test.js`; extend `cashier-discount.test.js`,
`cashier-full-discount.test.js`, `cashier-paid-swap.test.js`, `reports.discount-share.test.js`,
`reports.referral-full-price.test.js`, `refund-any.payment-log.test.js`; client
`cashier-discount-ui.test.mjs`, `cashier-refund-any.test.mjs`, `cashier-line-fix.test.mjs`,
`live-cashier.test.mjs`; RPC coverage guard.
